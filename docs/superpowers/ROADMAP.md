## 3. 必须现在决定的架构问题

### 3.1 图形界面怎么打包（影响 Phase 3 开工方式）

要拿**辅助功能**与**麦克风**权限，App 必须是有稳定签名、固定 bundle id 的 `.app`。当前工程是纯 SPM 命令行。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. SPM + 打包脚本**（推荐）| 保持 SPM，加一个 `.executableTarget` 做 SwiftUI App，写脚本组装 `.app` 目录、生成 Info.plist、`codesign` 签名 | 单一构建系统；无 `.xcodeproj` 需要维护；现有 CI/测试不变 | Info.plist、entitlements、签名要手写；Xcode 的界面预览用不上 |
| B. 独立 Xcode 工程 | 建 `.xcodeproj`，依赖本地 SPM 包 | 签名/entitlements/预览都是原生支持 | 多一套构建系统；`.xcodeproj` 是二进制式文本，改动难审查、易冲突 |

**决定：采用 A（SPM + 打包脚本）。用户 2026-08-05 拍板。**

理由有二，第二条是决定性的：

1. 本项目至今 40 余处缺陷全靠逐行 diff 审出来。`.xcodeproj` 是机器生成的大文件，改一个勾选项可能冒出几十行，审不动。
2. **本项目采用无人值守的子代理执行方式。** 无人值守时一切都要靠「读文本、改文本、验证文本」完成：
   - 建 `.xcodeproj` 而没有 Xcode 界面可点，就只能手写几千行的 pbxproj，这是最容易翻车的地方
   - Xcode 工程出错时报错含糊，标准解法是「在 Xcode 里点开看看」——而无人值守时点不了
   - 路 A 唯一真正的优点是 SwiftUI 实时预览，而**那是给人看的功能，对子代理价值为零**

**实时预览仍然保留**：界面代码放在 library target 里，用 Xcode 打开 `Package.swift` 即可预览；打包仍走脚本。两者不冲突。

**此决定可逆**：若打包踩坑代价过高，随时可切回 Xcode 工程。

**权限绑定 bundle id `com.ielts.speakingcoach`，一旦确定不得更改**（改了辅助功能授权会失效）。开发期必须用固定的自签名身份，ad-hoc 签名每次编译都变，会导致授权反复失效。

### 3.2 逐字稿怎么采集（影响 Phase 4）

设计稿每条训练记录都标着「N 条对话」，且复盘要「回到你真正说过的话」。

当前只在练习**结束后**取一次复盘。要拿逐字稿，必须在练习**进行中**持续采样 AX 树。

已知约束（spec 2.3.9）：**复盘在 AX 树里是碎片化的**，连定界标记都被拆成三段。逐字稿同理——需要按节点顺序拼接并去重。

设计要点：
- 每 2~3 秒采样一次，只取对话区的 `AXStaticText`
- 按内容哈希去重（流式输出会让同一条消息反复出现且不断变长，要保留最长版本）
- 采样失败不得中断练习——逐字稿是增强，不是必需

### 3.3 录音怎么做（影响 Phase 5）

设计稿：「保存我的回答录音」开关（默认关）、每条记录带播放器、可单独删除。

- 用 `AVAudioEngine` 录**麦克风**（不录系统音频——spec 第 10 节已明确不做 ScreenCaptureKit 双轨方案）
- 需要 `NSMicrophoneUsageDescription` 与 TCC 授权
- 存 `recordings/<sessionID>.m4a`，AAC 压缩
- **录音默认关闭**，与 spec 一致；开启需用户明确同意并记录 `recordingConsentAt`

**决定：只录麦克风，不录系统音频。用户 2026-08-05 拍板，理由是「有考官问过的文字就行」。**

回听时听到的是自己的发音、语调、卡顿；考官问了什么由**逐字稿**提供文字（Phase 4）。两者配合已覆盖「知道考官问了什么」这个需求。

不做系统音频的代价与收益已明确评估：

| | 只录麦克风（采用）| 加录系统音频（不做）|
|---|---|---|
| 权限 | 麦克风 | 麦克风 + **屏幕录制**（字面含义是「能看你屏幕」，观感偏重）|
| 实现 | 低 | 中——ScreenCaptureKit 指定只抓 ChatGPT 音频，再与麦克风混轨 |
| 风险 | 低 | 混轨的时间对齐、可能出现回声 |

**因此 Phase 4（逐字稿）对录音功能是前置依赖**，不只是并列关系——没有逐字稿，麦克风录音就缺了上下文。

## 3.4 无人值守执行下，哪些环节必须用户参与

本项目采用子代理无人值守执行。以下环节**任何自动化都绕不过去，也不应该绕过去**，需集中安排、避免零散打断：

| 环节 | 阶段 | 用户要做什么 |
|---|---|---|
| 给新 `.app` 授予辅助功能权限 | Phase 3 | 系统设置 › 隐私与安全性 › 辅助功能，勾选 |
| 授予麦克风权限 | Phase 5 | 弹窗点「允许」 |
| 真机联调（练一场、看效果）| 每个涉及 ChatGPT 的阶段 | 实际用一次并反馈 |
| 界面观感判断 | Phase 3 及之后 | 看着舒不舒服、顺不顺手 |

前两项是 macOS 的 TCC 机制决定的，一次性。后两项是**只有使用者能给的信息**——Phase 2 的六个真机缺陷里，有两个（Live 只能在全新会话启动、正确顺序是先 Live 后发消息）纯粹来自用户的使用经验，AX 树上完全看不出来。

## 4. 阶段划分

每个阶段独立可交付，完成后产品可用性都有实质提升。

### Phase 3 · 图形界面骨架 + 今日训练（最大一块）

**交付：一个能双击打开的 `.app`，全程不开终端就能选题、开练、看复盘。**

- SwiftUI App target + `.app` 打包脚本 + 固定签名身份
- 首次启动的辅助功能授权引导（spec 第 7 节：首次启动就引导，可跳过）
- 侧边栏导航骨架（十项，未实现的页面显示占位）
- **设计令牌与基础组件**（依据 `DESIGN-SYSTEM.md`）
- **今日训练**页：四条练习路线、本周进度、最近练习
- **训练题库**页：导入（含 **PDF**）、列表、按 Part 筛选
- **复盘报告**页：把已有的复盘 JSON 渲染成设计稿那样的分区视图
- **把练习驱动接进界面**：点「开始」真的能开练

依赖：无（Core 与 Bridge 已就绪）
风险：打包与签名是新领域，权限调试会反复

**范围调整（2026-08-05）：** 「驱动接进界面」原本排在 Phase 4，已提前到 Phase 3——否则 Phase 3 交付的「开始练习」按钮只会提示用户去敲命令，违反成品标准第 2 条。PDF 题库导入原本没排，也已补入：用户手上的季度题库就是 PDF，不做的话界面完成了也没题可练。

### Phase 4 · 逐字稿采集 + 训练记录

**交付：每次练习留下完整问答记录，训练记录页按月分组可回看。**

- 练习进行中持续采样 AX，拼接去重成 `PracticeSession.transcript`
- **训练记录**页：按月分组、每条显示日期/Part/题目/对话轮数/复盘状态
- 单条删除

依赖：Phase 3 的界面骨架
风险：采样与拼接的正确性——需要真机多轮验证

### Phase 5 · 录音与回听

**交付：可选开启录音，练完能回听自己的回答，可单独删除。**

- `AVAudioEngine` 麦克风录制 + 麦克风权限引导
- 训练记录页内嵌播放器
- 「保存我的回答录音」开关（默认关）+ 同意时间戳
- 单条录音删除；数据目录占用提示

依赖：Phase 4 的训练记录页
风险：音频权限与设备切换（插拔耳机）的处理

### Phase 6 · 复训中心

**交付：从复盘里挑一个目标，带着它重练，再换题验证。**

- **复训中心**页：待复训目标列表（来自 `RetrainingPolicy.rank`）
- 「带着本题进入复训」流程：回看证据 → 重答原题 → 撤掉提示
- 复训会话与普通练习的区分（复训时提示词要带上单点目标）
- 换题验证：同一目标换一道题再练

依赖：Phase 4（要能回看原答）
风险：低——`RetrainingPolicy` 已就绪，主要是流程与界面

### Phase 7 · 问题档案、词汇本、统计趋势

**交付：看见问题有没有变少。**

- **问题档案**页：错题按出现次数排序、「新问题」标记、趋势
- **我的词汇**页：词汇本、按优先级、可导出（对接你已有的 Anki 流程）
- 首页统计：本周 N/5 次目标、累计训练、本周开口时长、初步改善
- 「你的问题正在怎么变化」列表

依赖：Phase 4（统计需要训练记录）
风险：低

### Phase 8 · 学习计划页 + 完整练习路线

**交付：四条练习路线全部可用。**

- **学习计划**页：7/14/30 天周期、重点 Part 选择、每日拆分、进度
- 「按计划练今天」「继续上次练习」「复训一个旧问题」接通
- 计划调整与重新生成

依赖：Phase 6（复训路线）
风险：低——`PlanBuilder` 已就绪

### Phase 9 · MCP server + Codex 插件

**交付：能在 Codex 里调用。**

- `ielts-speaking-mcp` 可执行文件，7 个 tool（spec 4.4）
- `open_dashboard` 通过 `ieltscoach://` 唤起 App
- Codex 插件配置

依赖：Phase 3（需要 App 能被唤起）
风险：低——协议明确，与 Core 共享逻辑

### Phase 10 · 打包与分发

**交付：一个能给别人的 `.app`。**

- 图标、关于页
- Hardened Runtime、entitlements 定稿
- 公证脚本（不购买 Developer ID，架构预留）
- 首次使用引导

依赖：全部
风险：分发相关，本期不执行公证

## 5. 用户可配置项清单

设计稿强调「你始终可以按自己的状态开始」。以下全部由用户决定，不写死：

| 配置项 | 取值 | 默认 | 位置 |
|---|---|---|---|
| 反馈时机 | 全程零反馈 / 当场点出 | 全程零反馈 | 已实现（`FeedbackTiming`）|
| Part 2 准备时间 | 一分钟倒计时 / 自己决定 | 倒计时 | 已实现（`Part2PrepMode`）|
| **保存我的回答录音** | 开 / 关 | **关** | Phase 5 |
| **记录对话逐字稿** | 开 / 关 | **开** | Phase 4 |
| 练习路线 | 四选一 | 按计划练今天 | Phase 8 |
| 计划周期 | 7 / 14 / 30 天 | 用户选 | 已实现（`PlanBuilder`）|
| 重点 Part | Part 1 / 2 / 3 / 全真模考 | 用户选 | 已实现（`FocusPart`）|
| 每周训练目标 | 次数 | 5 次 | Phase 7 |
| 单次练习时长 | 分钟 | 按 Part 默认 | 已实现 |
| 单点目标 | 自由文本 | 空 | 已实现 |

**逐字稿默认开、录音默认关**：前者只多采集 AX 树（无隐私与权限成本，且是复盘质量的基础），后者涉及麦克风权限与磁盘占用，须用户明确同意。

## 7. 建议的执行顺序

**Phase 3 → 4 → 5 → 6 → 7 → 8 → 9 → 10**

理由：
- **3 先做**，因为现在所有能力都锁在命令行里，界面是可用性的分水岭
- **4 紧随其后**，因为逐字稿是复盘质量与训练记录的共同基础，越早开始积累越好
- **5 在 4 之后**，录音要挂在训练记录上
- **6、7、8 顺序可调**，都依赖 4 的数据
- **9、10 最后**，前者是额外通道，后者是交付形态

每个阶段开工前写详细实施计划，沿用已有流程：子代理实现 → 独立审查 → 突变验证 → 真机联调。
